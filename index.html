What GHAS actually is

GHAS is a set of security capabilities built into GitHub itself. Instead of sending code to an external scanner and waiting for a report, the analysis runs on GitHub's own infrastructure, against the repository, and writes results back into the developer's normal workflow.

Find flaws in your own code

Code Scanning analyses the source you write and flags issues such as SQL injection, cross-site scripting or unsafe deserialisation before they ever reach production.

In plain words: a very thorough reviewer that reads every line, every time, and never gets tired.

Stop credentials leaking

Secret Scanning looks for API keys, tokens, passwords and certificates in code, commits, issues and history, and can block a push that contains one.

In plain words: a bouncer at the door that checks nobody is carrying the office keys out of the building.

Fix instead of just report

Copilot Autofix proposes a concrete code change for most alerts. The developer reviews a suggested diff rather than reading a PDF finding and researching a remedy.

In plain words: the tool does not only say "this is broken", it offers the patch.
Naming note. GitHub restructured the bundle in 2025. What was sold as one "Advanced Security" add-on is now two products you can buy separately: GitHub Secret Protection (secret scanning, push protection, validity checks) and GitHub Code Security (code scanning with CodeQL, Copilot Autofix, dependency review, security campaigns). People still say "GHAS" for both together.

Capabilities

The two core features, explained simply

Code Scanning and Secret Scanning solve two different problems. One looks for mistakes in the logic you wrote. The other looks for credentials that should never have been committed at all.

Code Scanning

Code Security

Static analysis powered by CodeQL. Your code is turned into a queryable database, then hundreds of security queries run against it to trace how untrusted input flows through the application into a dangerous operation.

  • Runs on every pull request and on a schedule against the default branch.
  • Comments inline on the diff so the developer sees the problem at the exact line.
  • Data-flow aware, so it catches an unsafe path across several files, not just a bad-looking keyword.
  • Supports third-party scanners via SARIF upload, so existing tools report into the same alert list.
  • Copilot Autofix suggests the fix as a reviewable diff.
 Pull request #482 · checks
✕ HIGHSQL injection in api/orders.py:41
↳User input from request.args['id'] reaches cursor.execute() unsanitised
✓ FIXCopilot Autofix suggested: use a parameterised query
! MEDPath traversal in utils/files.py:88
✓47 other queries passed

Secret Scanning

Secret Protection

Pattern matching for credentials, built with more than 200 partner providers. It checks new commits, the full git history, plus issues, pull request bodies and descriptions.

  • Push protection rejects the push before the secret ever lands in the repository.
  • Validity checks ask the provider whether a found token is still live, so you triage real risk first.
  • Partner alerts notify the issuer (AWS, Azure, Stripe and others) so the credential can be revoked.
  • Historic scan of the whole repository, because a secret committed two years ago is still a secret.
  • Custom patterns for your own internal token formats.
 git push origin feature/payments
✕Push rejected — secret detected
·Type: Stripe live API key
·File: config/payments.env:12
·Status: active credential
→Remove the secret, or request a bypass with justification

The rest of the toolkit

Dependency review & Dependabot

Shows the security impact of a dependency change inside the pull request, and opens automated update PRs for vulnerable packages.

Why it matters: most application code today is other people's code.

Security overview

One org-level dashboard showing risk and coverage across every repository: which repos are enabled, where the open alerts sit, and how fast they are being closed.

Why it matters: security leads need the aggregate view, not 400 repo tabs.

Security campaigns

Bundle a set of existing alerts into a tracked remediation effort, assign them to the right teams, and drive the backlog down with Autofix suggestions attached.

Why it matters: turns a long alert list into finite, assignable work.

Software Development Lifecycle

Where GHAS sits in the SDLC

GHAS is not one gate at the end. It attaches to five points in the lifecycle, each with a different owner and a different cost of failure. The earlier a problem is caught, the cheaper it is to fix.

01 Code

In the editor

Secret scanning and code scanning results surface in the IDE, so problems are visible before a commit exists.

Owner: Developer
02 Commit

On push

Push protection blocks commits containing live credentials. The secret never enters git history.

Owner: Developer
03 Review

In the pull request

CodeQL analysis and dependency review run as checks. Findings appear as inline comments with suggested fixes.

Owner: Reviewer
04 Build

In CI/CD

Merge protection can require the security checks to pass. Third-party scanner results feed into the same alert model via SARIF.

Owner: Platform team
05 Operate

After release

Scheduled scans and new advisories re-evaluate code already shipped. Dependabot opens update PRs when a CVE lands.

Owner: Security team

Continuous, or an ad-hoc security exercise?

Continuous, and in parallel with development. This is the single biggest difference from a classic scanning tool.

Traditional security scan

Ad hoc

A separate team runs a tool at the end of a release cycle, or once a quarter. Results arrive as a report, days or weeks after the code was written. The developer has moved on to other work and has to reload the whole context to fix anything. Findings compete with feature deadlines and often lose.

Result: a backlog of stale findings and a late, expensive fix.

GHAS

Continuous

Analysis is triggered by the developer's own actions: every push, every pull request, plus a schedule on the default branch. The result lands within minutes, on the exact diff, while the code is still fresh in the author's head. Security work becomes part of the review, not a separate project.

Result: issues are fixed in the same pull request that created them.
Point-in-time scanning still has a place for penetration tests and compliance audits. GHAS does not replace those. It removes the routine, repeatable class of findings so the manual work can focus on what a scanner cannot see: business logic, authorisation design and architecture.

Developer workflow

What a developer actually experiences

Nothing here asks a developer to open a new tool, log into a separate console, or learn a new vocabulary. The security signal arrives inside the pull request they already had open.

09:14 · Writing code

The developer works normally

No agent to install per machine, no local scan to remember to run. Configuration lives with the repository.

09:41 · git push

A hardcoded key is blocked

Push protection rejects the push and names the credential type and file. The developer removes it, or requests a bypass that is logged for the security team.

09:46 · Pull request opened

Scans start automatically

CodeQL analysis and dependency review run as GitHub Actions checks, in parallel with the unit tests. Typical feedback within minutes.

09:53 · Review

Findings appear on the diff

Each alert is an inline comment on the offending line, with the data-flow path and severity. Copilot Autofix attaches a proposed code change the developer can commit directly.

10:02 · Merge

The gate is a branch rule, not a meeting

Branch protection can require the security checks to pass before merge. Clean code goes in. Accepted risk is documented as a dismissal with a reason.

Ongoing

Old code keeps being checked

Scheduled scans and new security advisories re-evaluate the default branch. If a dependency you shipped last year becomes vulnerable, Dependabot opens the update PR.

The case for it

Why Code Scanning and Secret Scanning matter

These two features cover the two most common and most damaging root causes of application breaches: a flaw in the code, and a credential that got out.

A leaked secret is immediately exploitable

A vulnerability needs an attacker to find and weaponise it. A live API key needs nothing. Public repositories are continuously scraped by automated tooling, and a committed cloud credential can be used within minutes of the push.

And: deleting the line does not help. The secret stays in git history until it is revoked. Push protection is the only reliable answer, because it stops the commit from happening.

Fix cost rises sharply with time

A vulnerability caught in a pull request is a small edit by the person who wrote the code. The same vulnerability found in production is an incident: triage, a hotfix, a release, possibly a disclosure and a customer conversation.

And: code review by humans does not scale to every line of every PR. Automated analysis does, and it never skips a file because the sprint is ending.

Pricing and the metered model

GHAS is licensed per active committer, billed monthly. An active committer is a developer who pushed at least one commit to a repository where the product is enabled, during that billing month. Someone who did not commit that month is not billed for that month.

How the metered model behaves

You pay for activity, not headcount

The count is derived from commits in the billing period, not from a static seat list. Contractors who finish an engagement drop out of the count automatically.

Committers are deduplicated

A developer working across ten enabled repositories is counted once, not ten times. The billing unit is the person in the enterprise, per month.

You can enable it gradually

Turn it on per repository or per organisation. Start with the repositories that carry real risk, watch the committer count, then widen the scope.

Prices are list prices for GitHub Enterprise Cloud and can change. Enterprise agreements, volume terms and GitHub Enterprise Server entitlements may differ. Confirm the current figures with your GitHub account team or on github.com/pricing before budgeting.

Common questions

Quick answers

The questions that come up most often in the first conversation about GHAS.

Does it slow down the pull request?

Scans run as checks in parallel with your existing tests, so they overlap with work that was happening anyway. Analysis time depends on repository size and language, and typically lands in minutes. You decide whether a failing security check blocks merge or is advisory.

Will developers be buried in false positives?

CodeQL traces actual data flow rather than matching keywords, which keeps noise well below a naive pattern scanner. Alerts can be dismissed with a documented reason, queries can be tuned per repository, and Copilot Autofix reduces the effort for the alerts that are real.

Does it replace our existing security tools?

Not necessarily. Third-party scanners can upload SARIF results into the same alert list, so GitHub becomes the single place developers look. Many teams keep a specialist tool and use GHAS as the always-on layer in the developer workflow.

What happens to secrets already in our history?

A historic scan flags them. The important step is revoking and rotating the credential, because it stays retrievable in git history even after the line is deleted. Push protection then prevents the next one from getting in.

Can we enable it for just some repositories?

Yes. Enablement is per repository, and can be applied at organisation level with security configurations so new repositories inherit the policy automatically. Billing follows the committers in the repositories you enabled.

Code Security / public-repo access

CodeQL code scanning

Find vulnerable patterns and data flows in your own source code. CodeQL is a static analysis engine; code scanning is where GitHub displays the results.

Illustrative exampleUser-controlled input flows into a SQL query without parameterization.

Runs: default setup scans on enablement, qualifying pushes/PRs, and an activity-dependent schedule.

Setup CodeQL

Need: repository admin or a role allowed to manage security settings, Actions enabled, and public visibility or Code Security entitlement. Default setup cannot coexist with an existing advanced setup.

  1. Open Settings > Advanced Security > Code Security.
  2. Under CodeQL analysis, select Set up > Default. Review detected languages and query suite.
  3. Enable CodeQL and check the first analysis. Use advanced setup if you need custom builds or workflow triggers.
Use it CodeQL

Open Security and quality > Code scanning, or a PR annotation. Inspect the rule and any data-flow path, assign an owner, then follow the code resolution workflow.

Verify: confirm a successful analysis for the expected language and commit, not just that the toggle is on.

Limits/cost: supported languages and query coverage only. Default-setup PRs from forks are excluded. Weekly scans require qualifying activity; inactive-repository scanning has separate organization settings. Private/internal use needs Code Security; Actions charges can apply.

Secret Protection / public-repo access

Secret scanning

Detect exposed credentials using supported provider patterns, with additional generic, custom, and AI detection options where available.

Illustrative example, fake valueAPI_TOKEN=DEMO_NOT_A_VALID_CREDENTIAL represents a leaked key. This placeholder is not a detection test.

Runs: scans existing repository history on enablement and new content as it is added, within supported detection scope.

Setup secret scanning

Need: admin/security-settings permission and Secret Protection for private/internal repositories. Public repositories have free supported secret scanning.

  1. Open Settings > Advanced Security > Secret Protection.
  2. Enable secret scanning if it is not already enabled. Review the initial history scan.
  3. Choose additional detection options deliberately. Before AI-detected push protection, set a hard Secret Protection AI credits budget.
Use it secret scanning

Open Security and quality > Secret scanning. Review the type, locations, and validity information when available. Start with revoke/rotate, not deleting the line.

Verify: confirm revocation with the issuer, then document remediation and resolve the alert with the correct reason.

Limits/cost: pattern and location coverage vary. Not every credential has a validity check. Generic and AI detections have additional limits and can be false positives. Private/internal entitlement and optional AI-credit charges are separate.

Secret Protection / public-repo access

Push protection

Block pushes containing supported secrets before GitHub accepts them. This is prevention at push time, separate from detecting secrets already present.

Illustrative exampleA contributor removes a detected token from every affected commit before retrying a blocked push.

Runs: during supported push and GitHub content-creation flows, not while you type.

Setup push protection

Need: repository admin/security-settings permission, secret scanning, and applicable Secret Protection entitlement.

  1. In Settings > Advanced Security > Secret Protection, enable repository push protection.
  2. Define who may bypass or approve bypass requests. Delegated bypass needs the appropriate paid feature.
  3. Tell contributors how to remove a secret from unpushed commits and how to request a legitimate bypass.
Use it push protection

Follow the blocked-push instructions. Rotate a real credential if exposed; remove it from all implicated commits. Review bypass alerts in Secret scanning.

Verify: check effective repository settings and audit a controlled, approved non-live test using the official instructions. Never push a real credential to test protection.

Limits/cost: only supported secrets and flows; bypasses and detection limits exist. User-level public-repo protection is not the same as repository protection. Optional AI-detected secret push protection consumes AI credits even if no secret is found.

Built in / no GHAS license required

Dependabot alerts

Match dependencies in the dependency graph against known vulnerabilities in the GitHub Advisory Database.

Illustrative exampleA new advisory affects the version of a library already in your lockfile.

Runs: when the graph changes or relevant advisory information changes.

Setup Dependabot alerts

Need: admin/security-settings permission and a supported manifest or submitted dependency graph.

  1. Open Settings > Advanced Security and enable the dependency graph.
  2. Enable Dependabot alerts.
  3. Check graph coverage and set notification/triage ownership.
Use it Dependabot alerts

Open Security and quality > Dependabot. Read the advisory, affected range and fix availability. Prioritize actual exposure and update the package.

Verify: inspect the dependency graph and confirm the alert no longer applies after an update lands.

Limits/cost: alerts are free for public and private repositories. Coverage depends on supported ecosystems and graph completeness. An alert does not guarantee an update PR or exploitability in your application.

Dependabot security updates

Try to open a pull request that upgrades a vulnerable dependency to a patched version.

Illustrative exampleAn alert leads to a patch-version update PR, linked back to the advisory.

Runs: in response to eligible Dependabot alerts with an available fix.

Setup security updates

Need: admin/security-settings permission, dependency graph, Dependabot alerts and a supported manifest/lockfile.

  1. Enable Dependabot security updates in Advanced Security settings.
  2. Configure access to private registries using Dependabot secrets if required.
  3. Decide whether to group updates and identify reviewers. Leave auto-merge off until your review/test policy is ready.
Use it security updates

Review the Dependabot PR, release notes, manifest and lockfile diff. Run compatibility tests before merging.

Verify: check the linked alert after merge and investigate Dependabot errors if no PR can be created.

Limits/cost: the basic feature is free on public/private repositories; CI on its PRs can have Actions costs. No compatible patch, registry access problems or ecosystem limits can prevent a PR. Premium custom auto-triage is separate.

Built in / no GHAS license required

Dependabot version updates

Keep dependencies current with scheduled update PRs, even when there is no security advisory.

Illustrative exampleA weekly PR updates a GitHub Action or application library to a newer release.

Runs: on the schedule you set in .github/dependabot.yml.

Setup version updates

Need: write access to add configuration, supported package ecosystem, registry access and repository policy allowing Dependabot.

  1. Add .github/dependabot.yml on the default branch.
  2. Set version: 2 and an updates entry with package ecosystem, manifest directory and schedule.
  3. Configure reviewers/groups and private registry secrets as needed. Review and merge the configuration.
Use it version updates

Review scheduled PRs like any dependency change. Check breaking changes, licenses and tests, not just version numbers.

Verify: open the repository's Dependabot update jobs and confirm a successful check of the intended directory.

Limits/cost: free for public/private repositories, separate from security updates and alert enablement. Ecosystem support, PR limits and registry access apply. CI and runner costs can still apply.

Code Security / public-repo access

Dependency review

See what a pull request changes in the dependency graph, including known vulnerable versions and license information.

Illustrative exampleA PR adds a dependency with a high-severity advisory. A configured review action fails its check.

Runs: review the PR dependency diff; the optional action runs on configured PR events.

Setup dependency review

Need: dependency graph, write access for a workflow, Actions, and Code Security for private repositories.

  1. Open a manifest/lockfile PR and inspect Files changed > Dependency review.
  2. For enforcement, add the official actions/dependency-review-action PR workflow with least-privilege contents: read.
  3. Choose severity/license policy; make its successful check required through a compatible ruleset.
Use it dependency review

Review added/removed packages and advisory links. Upgrade or replace a risky addition before merge.

Verify: confirm the action runs and the intended branch rule actually requires its check.

Limits/cost: public-repo access is free; private use requires Code Security. Actions usage may be billed. Supported graph data only; the diff view alone is not a merge gate.

Classic Autofix / no AI-credit charge

Copilot Autofix

Suggest a code change and explanation for supported code scanning findings. A suggestion is a starting point for review, not a verified fix.

Illustrative exampleAutofix proposes a parameterized query. A developer checks semantics and adds a regression test.

Runs: for supported findings in PRs or when a fix is requested for an eligible backlog alert.

Setup Copilot Autofix

Need: code scanning and public-repo access or Code Security. A separate Copilot subscription is not needed for classic Autofix.

  1. Enable code scanning and review enterprise/organization Autofix policy.
  2. Check the repository's Code scanning Autofix setting.
  3. Provide CI tests and reviewers before applying generated changes.
Use it Copilot Autofix

Open a supported alert or PR suggestion, read the explanation and full diff, edit as needed, then test and submit for review.

Verify: rerun analysis and functional/security tests. Confirm the alert status after merge.

Limits/cost: no guarantee a suggestion is available or correct. Classic Copilot Autofix does not consume AI credits. Agentic autofix is a separate capability that can prepare a draft fix PR and consumes Code Security AI credits and Actions minutes. Budget and enable it separately, then review and test its changes too.

Organization / applicable paid security product

Security campaigns

Group a bounded set of existing alerts into an owned remediation effort with a due date.

Illustrative exampleA security team asks repository owners to address a selected set of injection alerts before a release.

Runs: you create and publish a campaign; it tracks work against the selected alerts.

Setup security campaigns

Need: organization owner/security manager permissions, relevant alerts and Code Security for code campaigns or Secret Protection for secret campaigns.

  1. Open the organization's Security and quality > Campaigns > Create campaign.
  2. Choose a template or filter a focused set of alerts.
  3. Set a manager, due date and contact link. Review a draft, then publish.
Use it security campaigns

Assign owners, review progress and help teams resolve blockers. Code alerts may offer Autofix; exposed secrets still require issuer-side remediation.

Verify: inspect resolved alert states, not just assigned work or opened PRs.

Limits/cost: code campaigns use default-branch alerts. Secret campaigns are public preview with different tracking behavior. Agentic fix assignments can consume AI credits; a campaign is not automatic remediation.

Security overview

See adoption and risk across repositories you are allowed to view. Use Coverage to find missing controls, then risk views to prioritize findings.

Illustrative exampleA repository has no alerts because CodeQL was never enabled. Coverage makes that gap visible.

Runs: views reflect collected feature data; they do not initiate an exhaustive scan.

Setup security overview

Need: organization/enterprise access to security overview, appropriate security role and access to the underlying repositories/alerts.

  1. Open the organization's Security and quality tab.
  2. Use Coverage to inspect effective feature enablement.
  3. Filter risk and remediation views by repository/team and feature. Confirm the role sees the intended scope.
Use it security overview

Investigate uncovered repositories, assign owners and use campaigns for focused remediation. Export supported views as CSV where needed.

Verify: compare a known repository's settings and alert list with its overview entry and active filters.

Limits/cost: views and data depend on plan, enabled products and permissions. Enterprise organizations can view Dependabot data; paid security products unlock additional data. Default-branch views and empty alert lists are not evidence of full coverage.

03 / Use deliberately

AI Scan is three separate capabilities

They share an enterprise AI Scan policy, not one on/off switch or one coverage promise. Organizations enable each separately. Repository admins can opt out independently. Read each feature's availability and billing before you enable it.

Budget before enablement. Configure a hard Code Security AI credits budget with Stop usage when budget limit is reached. Organization PR-scan enablement can immediately enable eligible repositories and incur usage before repository admins opt out. Allowing an enterprise policy alone does not turn a feature on. Official billing rules.
PR changes / Code Security AI credits

AI Scan for pull requests

Find general security vulnerabilities in selected languages/frameworks outside CodeQL coverage, such as PHP or Terraform HCL.

Illustrative exampleA PHP change builds an unsafe SQL string from request input.

Runs: eligible PR creation and new commits.

Setup AI Scan for PRs

Need: code scanning enabled and an effective AI PR setting. Neither a Copilot license nor CodeQL default setup is required.

  1. Confirm eligibility and hard budget. Private/internal org repos need Code Security/GHAS; public org/personal repos do not need an active-committer license. Personal private and managed-user personal namespaces are excluded.
  2. Enterprise owner allows AI Scan. Org owner/security manager enables AI Scan for pull requests.
  3. Review affected repos. Org repo admins can opt out, not override a disabled org setting. Public personal-repo admins toggle it directly.
Use it AI Scan for PRs

Review AI-labeled findings in the PR Conversation/Files changed views, assess the risk and test the fix.

Verify: inspect the effective setting and an eligible PR's findings/reporting. No finding does not prove a scan found everything.

Limits/cost: advisory only, cannot block merges via rulesets. No fork PRs, Dependabot PRs or self-hosted runners. Selected coverage and possible false positives. Public access is not free AI usage. Credits are charged to the responsible billing account.

Default branch / public preview

AI Scan for repositories

Search your default-branch backlog across languages, including languages CodeQL already supports.

Illustrative exampleA maintainer requests a one-off scan for a risky authorization path in existing code.

Runs: on demand, not on push or a schedule.

Setup AI repository scans

Need: eligible repo and write access to run a scan. No Copilot license required. Public org/personal access is available; org private/internal repos need Code Security/GHAS. Personal private and managed-user personal namespaces are excluded.

  1. Review billing and set a hard Code Security AI credits budget.
  2. Enterprise allows AI Scan; org owner/security manager enables AI Scan for repositories. Org admins can opt out per repo but cannot override disabled org policy.
  3. From repository code scanning, start an on-demand AI Scan. Enabling the setting alone does not start a scan.
Use it AI repository scans

In Security and quality > Code scanning, filter by AI Scan. Assign, link issues or add findings to campaigns.

Verify after a fix: manually rerun. During preview an alert auto-closes only if the fix changes the exact triggering line; otherwise review and close it manually with evidence.

Limits/cost: each scan consumes Code Security AI credits, including public repos. The agent selects code within a time budget; it does not read every file in full. Default branch only, no automatic rescan, no self-hosted runners, and duplicate/inaccurate findings are possible.

AI applications / public preview

Scan for AI applications

Find risks specific to AI apps and agents. Current preview detection focuses on indirect prompt injection, not every AI security risk.

Illustrative exampleAn agent treats untrusted text from a fetched page as instructions to call a privileged tool.

Runs: eligible PR creation and new commits.

Setup AI application scanning

Need: eligible repository, code scanning, and the feature's own entitlement. Its docs require a GHAS license plus AI credits, including eligible public repositories. Do not reuse the public-repo licensing assumption from the other AI scans.

  1. Confirm availability for your account and set a hard AI-credit budget.
  2. Enterprise owner allows the shared AI Scan policy.
  3. Org owner separately enables Scan for AI applications. Repo admins may opt out. Enabling general AI PR Scan does not enable this detector.
Use it AI application scanning

Review AI app-labeled PR comments and proposed Autofix changes. Trace untrusted data into model/tool actions and test the trust-boundary fix.

Verify: confirm the separate setting and evaluate the relevant PR comment/fix. Review output rather than assuming an Autofix is correct.

Limits/cost: advisory, not a merge gate. PRs only, no backlog scan, fork or Dependabot PRs. No language/framework restriction is documented, but preview detection is limited to indirect prompt injection. AI credits are additional to the license. Its automatic Autofix behavior is independent of the CodeQL Autofix toggle.

04 / Fix

An alert is the start, not the outcome

These examples are illustrative, not live alerts or screenshots. Use the evidence and context to choose the right remediation. Code, secrets and dependencies need different responses.

Code

Trace it. Fix it. Rescan.

ILLUSTRATIVE ALERTSQL injection
request parameter > query builder > database
  1. Assess the alert. Read the rule, severity and affected branch. Inspect the source-to-sink data flow where available.
  2. Review the fix. Parameterize the query and preserve intended behavior. Review any Autofix as untrusted proposed code.
  3. Test. Add a regression case for malicious input, run existing tests and rerun the relevant analysis.
  4. Review and merge. Have the owner approve the full diff and required checks.
  5. Confirm resolution. Check the default-branch scan and alert status. For repository AI Scan, manually rerun and follow its preview closure rules.

Resolve code scanning alerts

Secrets

Revoke first. Then clean up.

ILLUSTRATIVE, NON-FUNCTIONAL VALUEExposed API credential
DEMO_NOT_A_VALID_CREDENTIAL
  1. Revoke or rotate at the issuer. Invalidate the exposed value. Coordinate replacement and dependent services.
  2. Remove the secret. Move credentials to a secret store. Assess history cleanup and coordinate it carefully if needed.
  3. Investigate exposure. Review issuer logs, scope, access and incident response requirements. A removed line does not invalidate a credential.
  4. Verify and document. Confirm the old value no longer authenticates; record actions without copying the secret into tickets. Resolve the alert with the accurate reason.
  5. Prevent recurrence. Check push protection and review any bypass.

Resolve secret alerts

Dependencies

Update without breaking behavior.

ILLUSTRATIVE ADVISORYVulnerable dependency
affected version > patched release
  1. Read the advisory. Check affected/fixed ranges, reachability and whether the dependency is direct or transitive.
  2. Review an update PR. Use Dependabot or create the change manually. Inspect release notes and the lockfile.
  3. Test compatibility. Run unit/integration tests and validate the vulnerable behavior. A compatibility score is not a substitute.
  4. Merge with review. Follow required checks and release policy. Deploy the patched build where applicable.
  5. Confirm resolution. Check the updated dependency graph and linked alert. If no patch exists, document mitigation and reassessment ownership.

Act on Dependabot alerts

Connect the workflow

Bring findings in. Send useful signals out.

An upload integration and a notification integration do different jobs. The labels below distinguish built-in capabilities from standards-based uploads and custom/API work. None implies a one-click connector.

Incoming / standards-based

Third-party scanner findings

Scanner → SARIF 2.1.0 → GitHub alert → PR fix

Use a scanner that emits GitHub-supported SARIF. GitHub displays uploaded findings; it does not run or license the vendor scanner for you.

Setup and verification SARIF uploads
  1. Confirm code scanning eligibility and scanner licensing. Configure SARIF 2.1.0 output with stable rule IDs and file locations.
  2. Upload using the official upload-sarif action, CodeQL CLI or REST API. Actions uploads need appropriate security-events: write; API credentials need code scanning write permission.
  3. Associate the correct commit/ref and analysis category. Verify the analysis and a finding's file/line in GitHub.

Limits: GitHub supports a subset of SARIF, with size/result limits. Not every vendor finding or remediation field maps to GitHub. Private/internal code scanning requires Code Security; vendor and CI costs are separate.

Incoming / custom CI integration

External CI/CD and CodeQL CLI

External CI → CodeQL / scanner → SARIF upload

Keep your existing CI system. Run CodeQL CLI or another compatible scanner there and send the results back to GitHub.

Setup and verification external CI
  1. Confirm CodeQL CLI entitlement, supported runner/build environment and repository access. Use advanced/external setup rather than conflicting default setup.
  2. In CI, check out the correct commit, create/analyze the CodeQL database (or run your scanner), and generate SARIF.
  3. Upload with a least-privilege GitHub App/token authorized for code scanning writes. Verify commit/ref, paths and the resulting analysis.

Limits: you own tool updates, builds, triggers, token rotation and failed-job monitoring. External analysis does not automatically configure a required merge check. This is not a way to run GitHub's AI Scan on a self-hosted runner.

Outgoing / custom webhook or API

Tickets and chat notifications

GitHub alert → Webhook / API → Ticket / notification

For example, route a code scanning alert to Slack using a custom webhook handler. A Jira ticket or Teams notification needs its own authorized destination API/app workflow, not an assumed native GHAS connector.

Setup and verification ticket and chat routing
  1. Install an approved app or create a webhook handler. Select the relevant supported events, such as code_scanning_alert, dependabot_alert or secret_scanning_alert.
  2. Authorize only required repository security-read/event permissions and destination scopes. Validate GitHub webhook signatures and protect delivery credentials.
  3. Map alert IDs to destination records. Handle retries, duplicates and state changes; test a delivery and resolution update.

Limits: event availability varies by alert type and access. Restrict recipients, redact sensitive payloads and link to GitHub rather than copying secrets. Acknowledging a ticket does not resolve a GitHub alert. App/vendor costs can apply.

Dashboards and SIEM

GitHub alerts → API / webhooks → Dashboard / SIEM

Use security-alert APIs or supported events to build a reporting feed. Assess a vendor connector's actual supported alert types and permissions before calling it integrated.

Setup and verification dashboards and SIEM

Scale after the pilot

Organization rollout is a separate job

A working repository configuration is the pilot, not an organization policy. Organization owners and security managers should agree on coverage, ownership and budgets before expanding.

Governance

Define and apply a baseline

  1. Inventory repositories. Record visibility, languages, owners, registry access and existing scanners. Estimate per-product active committers and AI/Actions exposure.
  2. Set enterprise policy and hard budgets. Treat AI policy allowance and org feature enablement as separate decisions.
  3. Create a security configuration. Enable applicable secret, dependency and CodeQL controls. Pilot a selected group before applying broadly or making it the default for new repositories.
  4. Handle exceptions. Use advanced CodeQL setup where default setup cannot meet build needs. Document opt-outs, bypass approvals and review dates.

Apply security configurationsCodeQL at scale

Operations

Prove coverage and keep it useful

  1. Inspect effective coverage. Review failed analyses, missing languages, disabled features and policy inheritance in security overview.
  2. Agree on review and merge rules. Require tests and appropriate code/dependency checks. AI advisory findings cannot be ruleset merge gates.
  3. Assign remediation. Name a triage owner and escalation path; use bounded campaigns for the backlog and an incident process for live secrets.
  4. Reassess regularly. Track unresolved risk, bypass reasons, scan health, committer licensing and AI usage. Empty alert lists do not prove safety.

Does this guide turn anything on in my repository?

No. It is a static learning guide, not connected to your account. The checklist stays in this page session and does not modify GitHub settings.

Are public repositories completely free?

No. A subset of security features is free on GitHub.com public repositories. AI Scan and agentic autofix can consume paid AI credits. AI application scanning documentation requires a GHAS license plus AI credits even for eligible public repositories. Check each feature, billing account and hard budget.

Can I require every AI finding to be fixed before merge?

Not through the AI Scan ruleset integration: AI PR and AI application findings are advisory and cannot enforce merge blocking. Use review policy alongside supported CodeQL, dependency-review and test gates. Do not confuse an AI comment with a required failed check.

Why is there no alert after I enable a feature?

Check eligibility, effective policy, completed analyses, supported language/manifest, branch and filters. An exhausted hard AI budget can prevent findings. No alerts can mean no finding, missing coverage or a scan that has not run. It is not a clean bill of health.

Does deleting a secret or dismissing an alert fix the risk?

No. Revoke/rotate a leaked credential at its issuer, remove it safely and investigate exposure. Dismiss code/dependency findings only with an evidence-based reason and an owner for any accepted risk.

How current is this guide, and does it apply to GHES?

AI behavior, billing and public list prices were checked against linked official documentation on 18 November 2026. Preview features can change. This guide targets GitHub.com / Enterprise Cloud, not blanket GHES availability. Confirm your GHES version's docs, contract and account eligibility before rollout. Prices are not a quote, and no AI-credit rate is invented here.
